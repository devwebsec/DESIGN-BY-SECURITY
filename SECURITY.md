# Security Policy

## Назначение

Настоящий документ определяет порядок обращения с сообщениями об уязвимостях
в репозитории **DESIGN-BY-SECURITY**, включая:

- контракт Design-by-Security ↔ Security Copilot v4;
- семантический валидатор (`tests/security-design-pipeline/semantic/`);
- интеграционный пайплайн (`security-design-integration.yml`);
- сборщик `.skill`-архива (`build-security-copilot.sh`).

Документ соответствует требованиям:
- **ГОСТ Р 56939-2024**, процессы №11 (анализ защищённости) и №23 (управление уязвимостями);
- **Приказ ФСТЭК России №117**, меры ЗИС.11, ЗИС.15, РСБ.1.

## Как сообщить об уязвимости

**НЕ создавайте публичные Issue** для проблем безопасности — это раскрывает
детали атаки до выпуска исправления.

Используйте один из защищённых каналов:

1. **GitHub Security Advisory** (предпочтительно)  
   Repository → **Security** → **Advisories** → **New draft security advisory**

2. **Корпоративный контур** (для внутренних контрибьюторов)  
   Обратитесь к владельцу процесса безопасной разработки (AppSec) через
   внутренние каналы SOC (создание тикета в Jira/OTRS с пометкой `SECURITY`).

### Что включить в отчёт

- Краткое описание (что нарушено: целостность, конфиденциальность, доступность).
- Версия контракта / коммит SHA, на котором воспроизводится.
- Шаги воспроизведения (PoC в изолированной среде).
- Оценка влияния на **CIA** и потенциальная связь с MITRE ATT&CK.
- Предлагаемое исправление (если есть).

## SLA обработки

| Этап                             | Срок реакции            |
| -------------------------------- | ----------------------- |
| Первичный ответ                  | 3 рабочих дня           |
| Триаж и оценка критичности       | 10 рабочих дней         |
| План устранения / митигации      | 30 рабочих дней         |
| Уведомление пользователей        | после выпуска патча     |

Критические уязвимости (CVSS ≥ 9.0 или прямой обход Security Gate)
обрабатываются вне очереди с уведомлением руководства ИБ в течение 24 часов.
## Safe Harbor

Мы не будем инициировать юридическое преследование против исследователей,
которые:

- действовали добросовестно и в рамках настоящей политики;
- не причинили вреда и не выходили за пределы минимально необходимого PoC;
- не раскрывали информацию третьим лицам до согласованной даты публикации.

Это не отменяет требований действующего законодательства РФ, но фиксирует
нашу позицию: ответственное раскрытие поощряется.
## Область ответственности

### Что покрывается политикой

- Обход hard-fail правил `evaluate.py` (например, скрытие critical_threat_without_requirement).
- Некорректная работа пайплайна, приводящая к пропуску уязвимостей в релиз.
- Уязвимости в `build-security-copilot.sh` (path traversal, отсутствие проверок целостности).
- Подмена содержимого `.skill`-архива (supply chain).
- Prompt-injection через артефакты Design-by-Security.

### Что НЕ покрывается

- Уязвимости в сторонних библиотеках (отдельный процесс — SCA / SBOM).
- Инфраструктурные проблемы GitHub Actions.
- Лицензионные споры.
